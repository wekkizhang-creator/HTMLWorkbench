# 页面加载性能优化设计

日期：2026-07-23

## 目标

在不改变上传、替换、回滚、下载和记录管理行为的前提下，缩短管理页首次打开和再次访问的等待时间，并让记录读取、刷新和上传过程始终有明确的加载反馈。

## 已确认的性能问题

- `public/brand-logo.png` 为 889,031 字节，但页面只以 42-52 像素展示。线上实测该文件下载耗时约 3.4-19.7 秒，是首屏最大的资源瓶颈。
- `app.js` 与 `styles.css` 合计约 33 KB，但自托管服务返回 `Cache-Control: no-cache`，且没有内容压缩。
- 页面启动时先请求 `/api/auth`，成功后才请求 `/api/uploads`，形成不必要的串行网络往返。
- 上传记录加载期间表格区域没有占位内容，弱网下表现为长时间空白。

## 方案

### 1. 静态资源瘦身

- 从现有 Logo 生成一份保持视觉一致的 128x128 优化图片，页面和图标统一引用该文件。
- 将首屏静态资源总传输体积控制在 100 KB 以内，Logo 文件目标不超过 60 KB。
- 不引入前端框架、打包器或运行时图片处理依赖。

### 2. 自托管静态响应优化

- 在 Node 静态文件响应中加入内存缓存，避免每次请求重复读取磁盘。
- 为静态资源生成 ETag，并正确处理 `If-None-Match`，未变化时返回 `304`。
- HTML 保持可及时更新；JS、CSS 和图片使用短期浏览器缓存与 `stale-while-revalidate`。
- 对支持 Gzip 的请求压缩 HTML、CSS、JS、JSON、SVG 和文本内容，并正确设置 `Vary: Accept-Encoding`。
- 保持 Vercel 行为兼容；Vercel 仍可使用平台自己的静态缓存和压缩能力。

### 3. 启动请求合并

- 管理页启动后直接请求 `/api/uploads`。
- 若接口返回 `401`，沿用现有逻辑跳转登录页，因此不再单独请求 `/api/auth`。
- 登录页面和退出登录流程保持不变。

### 4. Loading 状态

- 上传记录区域默认显示轻量骨架屏和“正在读取上传记录”，避免空白和布局跳动。
- 加载成功后切换为记录列表或空状态；加载失败时显示错误和可点击的重试入口。
- 刷新按钮在请求期间旋转并禁用，使用 `aria-busy` 表达状态。
- 上传期间保留现有禁用行为，同时显示旋转图标、`正在发布` 状态和明确的状态标签。
- Loading 只覆盖正在工作的区域，不使用阻塞整个页面的全屏遮罩。

## 数据流

1. 浏览器收到管理页 HTML 后立即绘制页面结构与记录骨架屏。
2. `app.js` 直接请求 `/api/uploads`。
3. `200`：写入记录状态，渲染列表、筛选项和统计数据。
4. `401`：跳转到带 `next` 参数的登录页。
5. 其他错误：保留页面结构，显示错误与重试按钮。
6. 后续刷新复用同一套加载状态，避免重复请求和重复状态逻辑。

## 错误处理

- 所有加载入口使用 `try/finally` 恢复按钮、`aria-busy` 和 loading 状态。
- 网络错误不清空已经成功显示的记录；首次加载失败才显示错误面板。
- 静态压缩或缓存处理失败时回退到原始文件响应，不影响页面可用性。
- 对 `HEAD`、条件请求和不支持 Gzip 的客户端保持正确响应。

## 验证

- `npm run check` 继续通过。
- 增加 Node HTTP 冒烟测试，验证静态资源状态码、缓存头、ETag/304、Gzip 和登录重定向。
- 增加资源体积检查，防止 Logo 再次膨胀。
- 验证管理页首次加载、空列表、已有记录、接口失败、刷新和上传六种状态。
- 在桌面与移动视口检查骨架屏、按钮 loading 和表格布局，确保没有重叠或明显布局跳动。
- 部署前后记录静态资源体积和请求数量，确认首屏少一次 API 请求且资源总量达到目标。

## 非目标

- 本轮不重构存储模型、ZIP 版本结构或 Vercel Blob 数据格式。
- 本轮不改变视觉主题、业务字段或权限规则。
- 本轮不增加 Service Worker，避免额外缓存一致性问题。
